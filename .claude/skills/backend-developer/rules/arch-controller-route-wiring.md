# Wire Every New or Changed Service Method to a Controller and a Route

## Why it matters

`arch-service-granularity` decides *where* new logic lives (a model's own service vs. an
exclusive service for a multi-model process) and `arch-command-steps` decides *how* it's
structured internally. Neither one says how that logic actually becomes reachable from the
outside — that's this rule. The real wiring, exactly as the generator produces it (see
`apps/api/src/routes/data_model.js`, `controllers/data_model.js`, `routes/index.js` in the
`backend` example project):

- A **router** class returns `{ modelPath, paths }`, where each entry in `paths` is
  `{ requestMethod, path, controllerMethod }` and `controllerMethod` is a **bound** method
  pulled straight from a controller instance.
- A **controller** binds each of its methods in its constructor
  (`this.add = this.add.bind(this)`) and only translates `req`/`res` — it delegates the actual
  work to a service.
- Every router gets instantiated and collected once, in `routes/index.js`'s `Routes` class.

A model generated by the CLI already gets this wiring for its six CRUD methods automatically.
What's missing once you start writing custom logic (per `arch-service-granularity`) is knowing
**which of three things to do** with the controller and the routes file. There are exactly three
cases.

## Case 1 — A generated CRUD action needs extra steps: repoint the controller, leave the route alone

When business logic from `DOCUMENTATION.md` says creating one model must also modify other
records (e.g. creating a `Sale` must decrement `Stock`), that's a multi-model process — per
`arch-service-granularity` it gets its **own exclusive service**. Structure it as steps
(`arch-command-steps`) and make its **last step reuse the model's own existing service method**
(`SaleService.add`) instead of re-implementing creation — that method already has the right
validation and contract applied, don't duplicate it.

Then **edit the existing controller method** so it calls the new exclusive service instead of the
model's own service directly. The route entry doesn't change at all — same path, same HTTP
method, same `controllerMethod` reference (`this.saleController.add`); only what `add` calls
*inside* changes.

```javascript
// services/saleProcessing.js  (NEW exclusive service — arch-service-granularity)
const SaleService = require('./sale')
const DecrementStock = require('./commands/decrementStock')

class SaleProcessingService {
	constructor() {
		this.saleService = SaleService.getInstance()       // reuse, don't duplicate
		this.decrementStock = DecrementStock.getInstance()  // a command step
	}

	static getInstance() {
		if (!this.instance) this.instance = new SaleProcessingService()
		return this.instance
	}

	async createSale(config = {}) {
		await this.decrementStock.execute({ items: config.body.items })
		return await this.saleService.add(config)   // last step: the original generated method
	}
}
module.exports = SaleProcessingService
```

```javascript
// controllers/sale.js  (EXISTING controller — only the body of `add` changes)
const SaleProcessingService = require('../services/saleProcessing')
// ...
constructor() {
	// ...
	this.saleProcessingService = SaleProcessingService.getInstance()
	this.add = this.add.bind(this)
}

async add(req, res) {
	try {
		const sale = await this.saleProcessingService.createSale({ body: req.body, files: req.files }) // ← was this.saleService.add(...)
		const response = this.handleResponseHandler.buildResponse(sale)
		res.status(response[this.responseBody.STATUS]).json(response)
	} catch (error) {
		// ...same error handling as the generated controller
	}
}
```

`routes/sale.js` is untouched — `{ requestMethod: 'post', path: '', controllerMethod: this.saleController.add }`
still points to the same controller method; that method just does more now.

## Case 2 — A new non-CRUD action on the same model, served to a frontend: extend its existing controller and routes file

This is how to implement a custom action `architect` already wrote a contract for (e.g. "cancel a
Sale", `art-artifact-contracts`'s non-CRUD case) when it belongs to a model that already has a
generated controller/router. Decide where the logic lives with `arch-service-granularity` as
usual, then:

1. Add the new method to the model's **existing** service (or call into an exclusive service, per
   the granularity decision).
2. Add the new method to the model's **existing** controller, bound in the constructor exactly
   like the generated ones.
3. Add **one more entry** to the same router's `paths` array — never a second router for the same
   model.

```javascript
// controllers/sale.js — one more bound method, same file as add/findOne/list/...
this.cancel = this.cancel.bind(this)

async cancel(req, res) {
	try {
		const sale = await this.saleService.cancel({ id: req.params.id })
		const response = this.handleResponseHandler.buildResponse(sale)
		res.status(response[this.responseBody.STATUS]).json(response)
	} catch (error) {
		console.error(error)
		const response = this.handleResponseHandler.buildResponse(error)
		res.status(response[this.responseBody.STATUS]).json(response)
	}
}
```

```javascript
// routes/sale.js — one more entry in the SAME paths array used for CRUD
{ requestMethod: 'post', path: '/:id/cancel', controllerMethod: this.saleController.cancel }
```

## Case 3 — The same module, but a genuinely different consumer: its own controller and routes file (rare)

Only when a second frontend needs its own exposure of essentially the same underlying data —
e.g. an admin panel uses the generated `sale` controller/router directly, but a separate
customer-facing frontend needs a distinctly shaped, separately-authorized surface over sales
(a `payments` service) — create a **new** controller and a **new** routes file, with their own
`modelPath`, and register the new router in `routes/index.js` exactly like `health`,
`data_model`, and `sub_data_model` already are. Its methods should still call into the existing
service(s) (`SaleService`/`SaleProcessingService`) rather than re-implementing the logic.

```javascript
// controllers/payments.js (NEW) — calls the SAME services as the sale controller
// routes/payments.js (NEW) — its own modelPath, e.g. '/payments'
```

```javascript
// routes/index.js — register the new router alongside the existing ones
const PaymentsRouter = require('./payments')
// ...
this.paymentsRouter = PaymentsRouter.getInstance().getRoutes()
// ...
return { ..., paymentsRouter: this.paymentsRouter }
```

This is the exception, not the default: `architect`'s own design usually has one frontend artifact
calling every microservice through its one generated controller per model (see `art-identify-artifacts`),
so a second controller over the same data only makes sense when the user explicitly asks for a
separately-exposed surface — never invent one on your own.

## Key Rules

1. Every new or changed service method must end up reachable through a **bound controller
   method** and a **routes `paths` entry** — never leave business logic unreachable, and never
   add a route with no controller method or vice versa.
2. **Case 1** (extending a generated CRUD action): create the exclusive service per
   `arch-service-granularity`, have it reuse the original model service's method as its last step,
   and repoint the *existing* controller method to it. The route entry never changes.
3. **Case 2** (new non-CRUD action, same model): add one method to the model's *existing*
   controller and one entry to its *existing* router's `paths` array. Never create a second
   controller or router for a model that already has one.
4. **Case 3** (same module, different consumer): create a new controller + new routes file and
   register it in `routes/index.js` — only when a genuinely different frontend/consumer needs its
   own exposure of the same data, never as a default choice.
