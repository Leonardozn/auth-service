# Every service method and command needs its own unit test

## Why it matters

A service method (`arch-services-layer`) or a command's `execute` method
(`arch-command-steps`) is not done when it returns the right value once in manual
testing — it's done when it has its own `node:test` file proving that. The project
already ships with this discipline wired in: every CRUD service method generated by
`easy-node` (`add`, `findOne`, `list`, `update`, `replace`, `remove`) has a matching
unit test under `apps/<app>/tests/unit/services/<model>.test.js`, with the repository
mocked via `apps/<app>/tests/support/mock-repository-preload.js`. Any method or command
*you* add must follow the exact same pattern — it is not optional polish.

## Incorrect Example

Adding a new command/service method and stopping at the controller/route wiring.

```javascript
// services/commands/calculateTotal.js — new command, no test anywhere
class CalculateTotal {
	static getInstance() {
		if (!this.instance) this.instance = new CalculateTotal()
		return this.instance
	}

	async execute({ items = [] }) {
		return items.reduce((total, item) => total + item.price, 0)
	}
}
module.exports = CalculateTotal
// ❌ wired into checkout.js and shipped — no tests/unit/services/commands/calculateTotal.test.js
```

## Correct Example

The command ships with its own test, written the same way the generated model tests are.

```javascript
// tests/unit/services/commands/calculateTotal.test.js
const { test } = require('node:test')
const assert = require('node:assert/strict')
const CalculateTotal = require('../../../../src/services/commands/calculateTotal')

test('CalculateTotal — sums item prices', async () => {
	const command = CalculateTotal.getInstance()

	const result = await command.execute({ items: [{ price: 10 }, { price: 25 }] })

	assert.equal(result, 35)
})

test('CalculateTotal — returns 0 for an empty list', async () => {
	const command = CalculateTotal.getInstance()

	const result = await command.execute({ items: [] })

	assert.equal(result, 0)
})
```

## Key Rules

1. A new service method or command `execute` method is incomplete until it has its own
   `node:test` file — treat it with the same priority as `arch-controller-route-wiring`.
2. Cover the method's distinct behaviors as separate `test()` blocks (happy path, empty/edge
   input, error path), not one test that only checks the method "ran".
3. Use `node:test` — the project's generated tests already use it (no Jest/Mocha to add).
4. See `test-mirror-and-mock` for where the test file goes and how to mock its dependencies.
